[abstract]
--
Using Terraform, create an Amazon EKS cluster with a GPU NodePool, set up monitoring, and create an Amazon S3 bucket for model storage. Choose between EKS Auto Mode (managed compute) or self-managed OSS Karpenter.
--

This section of the guide walks you through the steps to create the infrastructure required to run GPU workloads on Amazon EKS. These steps include an EKS cluster, GPU compute with EKS Auto Mode and Karpenter, a monitoring stack, and Amazon S3 storage for model weights.

## Download the Terraform code

There are two deployment options for the Amazon EKS cluster: a cluster with EKS Auto Mode or self-managed OSS Karpenter. 

[IMPORTANT]
====
Choose either EKS Auto Mode or self-managed OSS Karpenter path and use it throughout the guide.
====

To begin confiuguring and deploying the required infrastructure, download the Terraform code used in this user guide:

[role="tablist"]
EKS Auto Mode::
+
[source,bash]
----
REPO=git@ssh.gitlab.aws.dev:dmitrynutels/content/ai-on-eks/user-guide.git
BRANCH=split-003
DST=eks-docs-inf

git clone --depth 1 --branch "${BRANCH}" --filter=blob:none --sparse "${REPO}" "${DST}"
cd "${DST}"
git sparse-checkout set "terraform/auto-mode" "scripts"
mv terraform/auto-mode/* terraform/
rmdir terraform/auto-mode
rm -rf .git
----

Self-managed Karpenter::
+
[source,bash]
----
REPO=git@ssh.gitlab.aws.dev:dmitrynutels/content/ai-on-eks/user-guide.git
BRANCH=split-003
DST=eks-docs-inf

git clone --depth 1 --branch "${BRANCH}" --filter=blob:none --sparse "${REPO}" "${DST}"
cd "${DST}"
git sparse-checkout set "terraform/karpenter" "scripts"
mv terraform/karpenter/* terraform/
rmdir terraform/karpenter
rm -rf .git
----

These commands, for either EKS Auto Mode or self-managed Karpenter, create the folder structure under the `${DST}` folder (`eks-docs-inf` by default):

----

├── terraform
│   ├── manifests/...
│   ├── eks.tf
│   ├── ...
│   ├── main.tf
│   ├── ...
│   ├── variables.yt
│   └── vpc.tf
└── scripts
    └── cleanup.sh
----

The following diagram shows both EKS Auto Mode and self-managed OSS Karpenter configurations and the differences between them.

.EKS cluster options: Auto Mode and self-managed Karpenter
image::images/ai-ml-inference-cluster-setup-cli-cluster-options.png[High-level architecture showing the EKS cluster with EKS Auto Mode or self-managed OSS Karpenter paths and the differences between them.,width=75%]

On a high level, thes options differ in the way they provision the EKS cluster and its add-ons:

* **EKS Auto Mode:** On top of its https://docs.aws.amazon.com/eks/latest/userguide/eks-add-ons.html#addon-consider-auto[standard managed capabilities], Auto Mode includes the following GPU-relevant managed capabilities: https://github.com/aws/eks-node-monitoring-agent[EKS Node Monitoring Agent], https://docs.aws.amazon.com/eks/latest/userguide/node-repair.html[Automatic node repair], https://github.com/awslabs/soci-snapshotter[Seekable OCI (SOCI) snapshotter]. The Bottlerocket EKS-optimized accelerated AMI that Auto Mode launches for GPU nodes also includes NVIDIA device plugin.

* **Self-managed OSS Karpenter:** On an EKS standard cluster, you install and configure all of the above yourself, plus standard add-ons such as CoreDNS, the VPC CNI, and kube-proxy, and create your own Ec2NodeClass. This walkthrough does not install the EBS CSI driver, the default gp3 StorageClass, or the {aws} Load Balancer Controller that EKS Auto Mode includes by default.

The `git clone` command copies the required Terraform code to start provisioning the environment's infrastructure components. The two provision options follow the high-level architecture diagram at the top of the page, and share the monitoring following components, which include:

* **`main.tf`:** {aws}, helm, Kubernetes, kubectl provider configs and EKS auth wiring.
* **`versions.tf`:** Terraform and provider versions.
* **`variables.tf`:** User-facing knobs (region, deployment name, mode toggle, allowed CIDRs, and so on).
* **`outputs.tf`:** Post-apply outputs (cluster name, region, kube-config command).
* **`vpc.tf`:** VPC, subnets across three AZs, Internet Gateway + NAT, VPC endpoints, and EKS-discovery tags.
* **`s3.tf`:** The S3 bucket to store model weights.
* **`monitoring.tf`:** The monitoring infrastructure resources.

The two provision options share the monitoring components, which include:

* **kube-prometheus-stack:** Uses the https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack[community Helm chart] that bundles the Prometheus Operator, a Prometheus StatefulSet, kube-state-metrics, prometheus-node-exporter, and Grafana.
* **DCGM exporter:** The https://github.com/NVIDIA/dcgm-exporter/tree/main/deployment[NVIDIA DCGM Exporter DaemonSet] that exposes GPU metrics (utilization, memory, power, temperature, and so on) as Prometheus metrics.
* **Amazon Managed Prometheus (AMP) workspace:** {aws}-managed Prometheus storage backend.
* **AMP remote-write permissions:** Provides the in-cluster Prometheus `aps:RemoteWrite` permissions for the AMP workspace.
* **AMP query permissions:** Provides the in-cluster Grafana `aps:QueryMetrics`/`GetSeries`/`GetLabels`/`GetMetricMetadata`/`DescribeWorkspace`/`ListWorkspaces` permissions for the AMP workspace.

Both options also share the `scripts` folder, which includes two helper scripts that provision and tear down the environment:

* **`scripts/install.sh`:** `terraform init` + `terraform apply`.
* **`scripts/cleanup.sh`:** controlled cleanup and `terraform destroy`.

The following files contain most of the differences between EKS Auto Mode and Self-managed OSS Karpenter provision:

* **`eks.tf`:** EKS cluster configured to use Auto Mode (which includes add-ons such as CoreDNS, VPC CNI, kube-proxy, and so on) or OSS Karpenter that installs these add-ons explicitly
* **`nodepools.tf`:** EKS Auto Mode or OSS Karpenter configuration loading.
* **`manifests/*`:** EKS Auto Mode or OSS Karpenter YAML configuration files, loaded dynamically by Terraform via `nodepools.tf`.

## Set environment variables

To ensure successful deployment, you need to define a region where to deploy the infrastucture. We've also included a default value for the deployment name, which is used for the EKS cluster and as a prefix for other infrastructure components.

You can override the region and the deployment name values by setting the following environment variables in the terminal session (with values of your choice).

[NOTE]
====
We excluded the aAvailability Zones use1-az3, usw1-az2, and cac1-az3, because Amazon EKS does not support control plane placement in those zones. Creating a cluster with subnets in any of these zones results in an UnsupportedAvailabilityZoneException.
====

Define (and adjust as required) the environment variables:

[source,bash]
----
export AWS_REGION=us-east-2
export CLUSTER_NAME=eks-docs-inf 
export TF_VAR_region=${AWS_REGION}
export TF_VAR_deployment_name=${CLUSTER_NAME}
----

[IMPORTANT]
====
By default, the provisioned cluster endpoint is opened for both public (`0.0.0.0/0`) and private access. The CIDR for the public access is defined in the `variables.tf` file as `var.allowed_cidrs`, which you can override by setting the `TF_VAR_allowed_cidrs` environment variable with a comma-separated list of CIDRs.
====

[source,bash]
----
# Optional, but recommended: restrict public access CIDR to your current IP address
export TF_VAR_allowed_cidrs="[\"$(curl -s https://checkip.amazonaws.com)/32\"]"
----

[NOTE]
====
Keep these environment variables' values consistent in your terminal. Changing or removing them can cause subsequent commands to fail or target the wrong region/cluster.
====

Self-managed Karpenter::
+
**Enable Automatic Node Repair**
+
EKS Auto Mode enables automatic node repair by default. On a cluster with a self-managed OSS Karpenter it is placed behind the `NodeRepair=true` Karpenter feature gate and must be turned on explicitly. When enabled, Karpenter reads the node conditions set by the Node Monitoring Agent (`AcceleratedHardwareReady`, `KernelReady`, `NetworkingReady`, `ContainerRuntimeReady`, `StorageReady`) and replaces unhealthy nodes automatically. Node Monitoring Agent is one of the add-ons we install for the cluster.
+
In the Terraform code we've already created `enable_karpenter_node_repair` variable, set to `false`, that feeds the Karpenter configuration and the above `TF_VAR_enable_karpenter_node_repair=true` enables the `NodeRepair`.
+
**Install NVIDIA device plugin**
+
The NVIDIA device plugin advertises the `nvidia.com/gpu` resource on GPU nodes so Kubernetes recognizes them as schedulable for GPU pods. The EKS-optimized Bottlerocket Accelerated AMI pre-installs the device plugin, while the EKS-optimized AL2023 NVIDIA AMI does not. Auto Mode uses the Bottlerocket Accelerated AMI for its GPU nodes, which is why no manual install is needed there. The OSS Karpenter path walkthrough uses AL2023, so we install the device plugin as part of the Terraform deployment.
+
In the Terraform code we configured the plugin with the equivalent of the following Helm chart values:
+
[source,yaml]
----
nodeSelector:
  amiFamily: al2023

tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule

# DaemonSet - only on al2023 GPU nodes
gfd:
  enabled: true
  nodeSelector:
    amiFamily: al2023
  tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule

nfd:
  # Land on system MNG (CriticalAddonsOnly-tainted)
  master:
    nodeSelector:
      node-role: system
    tolerations:
      - key: CriticalAddonsOnly
        operator: Exists

  # Land on system MNG (CriticalAddonsOnly-tainted)
  gc:
    nodeSelector:
      node-role: system
    tolerations:
      - key: CriticalAddonsOnly
        operator: Exists

  # DaemonSet - only on al2023 GPU nodes
  worker:
    nodeSelector:
      amiFamily: al2023
    tolerations:
      - key: nvidia.com/gpu
        operator: Exists
        effect: NoSchedule
----
+
The `amiFamily: al2023` label is not set automatically by EKS. You apply it on the GPU NodePool template in the next section so that nodes Karpenter launches advertise themselves as AL2023, and the device plugin DaemonSet selects them. If you later add a Bottlerocket NodePool to the same cluster, you would label it `amiFamily: bottlerocket` and add `nvidia.com/gpu.deploy.device-plugin: "false"` so the device plugin DaemonSet skips those nodes (Bottlerocket already has it built in).
+
The https://github.com/NVIDIA/k8s-device-plugin/tree/main/deployments/helm/nvidia-device-plugin[nvidia-device-plugin chart] bundles four main components:
+
* **The device plugin:** This is a DaemonSet that advertises `nvidia.com/gpu` to Kubernetes so pods can request GPUs. Configuring `nodeSelector` to `amiFamily: al2023` and adding the `nvidia.com/gpu` toleration limits its scheduling to EKS-optimized AL2023(AL2023) NVIDIA AMI GPU nodes only, which in this cluster are only nodes created through the Karpenter GPU NodePool.
+
* **GPU Feature Discovery (GFD):** This is a DaemonSet, enabled via `gfd.enabled: true`, that reads each GPU's properties (model, memory, compute capability, driver version) and publishes them as node labels (`nvidia.com/gpu.product=L4`, and so on). Similar to the device plugin, we limit the DaemonSet to the GPU nodes with AL2023 GPU AMIs.
+
* **Node Feature Discovery (NFD):** This is another DaemonSet, required by GFD, that reports instance features (similar to GFD, but generic ones) and can run on any instance, but for the purposes of this guide we limit the DaemonSet to the GPU nodes with AL2023 GPU AMIs. The management components of the NFD are regular Deployments, so we schedule them on the system Managed Node Group (MNG) nodes instead, the same way we do it for all non-DaemonSet operational components.

## Attach an On-Demand Capacity Reservation (ODCR)

In this section we will create an https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/capacity-reservation-overview.html[On-Demand Capacity Reservation (ODCR)] for one GPU instance to allow EKS Auto Mode and self-managed Karpenter to provisions nodes from the reserved capacity first, and once it's consumed, to use spot or on-demand based on pricing and availability.

[role="tablist"]
EKS Auto Mode::
+
EKS Auto Mode dynamically provisions suitable EC2 instances, based on its configuration and workload requirements. It includes a `default` NodeClass and `system` and `general-purpose` https://docs.aws.amazon.com/eks/latest/userguide/set-builtin-node-pools.html[built-in] NodePools, designed to provide flexible compute for your workloads.
+
View the default Auto Mode configuration:
+
[source,bash]
----
kubectl get nodepools,nodeclasses
----
+
Expected output:
+
[source,text]
----
NAME                                    NODECLASS   NODES   READY   AGE
nodepool.karpenter.sh/general-purpose   default     0       True    63m
nodepool.karpenter.sh/gpu-inf           gpu-inf     0       True    61m
nodepool.karpenter.sh/system            default     1       True    63m

NAME                                  ROLE                                               READY   AGE
nodeclass.eks.amazonaws.com/default   eks-docs-inf-eks-auto-...                          True    63m
nodeclass.eks.amazonaws.com/gpu-inf   eks-docs-inf-eks-auto-...                          True    30m
----
+
While the default `system` and `general-purpose` NodePools shown above are suitable for most workloads, if a workload requires changes to storage, compute, or networking configurations, you can create custom NodePools and NodeClasses by using EKS Auto Mode.
+
To be able to deploy inference workloads that require GPU instances, as part of the Terraform code, we created the `gpu-inf` NodePool, that looks like this:
+
[source,yaml]
----
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: gpu-inf
spec:
  template:
    metadata:
      labels:
        guide: eks-docs-inf
    spec:
      nodeClassRef:
        group: eks.amazonaws.com
        kind: NodeClass
        name: gpu-inf
      taints:
        - key: nvidia.com/gpu
          effect: NoSchedule
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ['spot', 'on-demand', 'reserved']
        - key: eks.amazonaws.com/instance-category
          operator: In
          values: ['g']
        - key: eks.amazonaws.com/instance-generation
          operator: Gt
          values: ['4']
        - key: kubernetes.io/arch
          operator: In
          values: ['amd64']
----
+
[NOTE]
====
For reference, you can view the `general-purpose` NodePool by executing `kubectl get nodepool general-purpose -o yaml` in your terminal.
====
+
The `gpu-inf` NodePool does two things differently from the built-in `general-purpose` NodePool: it lists `reserved` as a capacity type option and references a new custom `gpu-inf` NodeClass. It is enough for a common GPU-oriented use case, to use the `default` NodeClass in the NodePool above. To make use of an ODCR, we need to pass the capacity reservation ID to a custom NodeClass, configured at via the `capacityReservationSelectorTerms` parameter.
+
For this purpose, as part of the Terraform code, we defined the `gpu-inf` NodeClass that looks like this:
+
[source,yaml]
----
apiVersion: eks.amazonaws.com/v1
kind: NodeClass
metadata:
  name: gpu-inf
  labels:
    guide: eks-docs-inf
spec:
  role: ${node_iam_role_name}
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: ${cluster_name}
        kubernetes.io/role/internal-elb: '1'
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: ${cluster_name}
  capacityReservationSelectorTerms:
    - id: ${capacity_reservation_id}
----
+
When we executed the `./scripts/install.sh` command, Terraform replaced the tokens: the `cluster_name` with the name of the cluster and the `node_iam_role_name` with the automatically created `eks-docs-inf-eks-auto-...` (also visible in the output above) IAM node role. Terraform also ignored the `capacity_reservation_id`, as the `capacity_reservation_id` Terraform variable default value is set to `""`.
+
If we were to deploy a workload that requires a GPU and matches the `gpu-inf` NodePool, a spot or on-demand instance would be provisioned instead.

Self-managed Karpenter::
+
EKS Auto Mode dynamically provisions suitable EC2 instances, based on its configuration and workload requirements. It bundles both into a single NodeClass and NodePool pair. Karpenter uses an EC2NodeClass (the {aws}-specific launch template equivalent) and a NodePool (the scheduling policy). To be able to deploy inference workloads that require GPU instances, we created a coresponding EC2NodeClass and NodePool as part of the Terraform code.
+
View the Karpenter configuration:
+
[source,bash]
----
kubectl get nodepools,ec2nodeclasses
----
+
Expected output:
+
[source,text]
----

nodepool.karpenter.sh/gpu-inf   gpu-inf     0       True    8m23s

NAME                                     READY   AGE
ec2nodeclass.karpenter.k8s.aws/gpu-inf   True    10m
----
+
To be able to deploy inference workloads that require GPU instances, as part of the Terraform code, we created the `gpu-inf` NodePool, that looks like this:
+
[source,yaml]
----
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: gpu-inf
spec:
  template:
    metadata:
      labels:
        guide: eks-docs-inf
        amiFamily: al2023
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: gpu-inf
      taints:
        - key: nvidia.com/gpu
          effect: NoSchedule
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ['spot', 'on-demand', 'reserved']
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ['g']
        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ['4']
        - key: kubernetes.io/arch
          operator: In
          values: ['amd64']
----
+
For the purposes of this guide, the `gpu-inf` NodePool defines two things: it lists `reserved` as a capacity type option and references a new custom `gpu-inf` EC2NodeClass. To make use of an ODCR, we need to pass the capacity reservation ID to the corresponding EC2NodeClass, configured at via the `capacityReservationSelectorTerms` parameter.
+
For this purpose, as part of the Terraform code, we defined the `gpu-inf` EC2NodeClass that looks like this:
+
[source,yaml]
----
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: gpu-inf
spec:
  role: ${node_iam_role_name}
  amiSelectorTerms:
    - alias: al2023@latest
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: ${cluster_name}
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: ${cluster_name}
%{ if capacity_reservation_id != "" }  
  capacityReservationSelectorTerms:
    - id: ${capacity_reservation_id}
%{ endif ~}
  instanceStorePolicy: RAID0
  userData: |
    apiVersion: node.eks.aws/v1alpha1
    kind: NodeConfig
    spec:
      featureGates:
        FastImagePull: true
----
+
When we executed the `./scripts/install.sh` command, Terraform replaced the tokens: the `cluster_name` with the name of the cluster and the `node_iam_role_name` with the automatically created `eks-docs-inf-eks-auto-...` (also visible in the output above) IAM node role. Terraform also ignored the `capacity_reservation_id`, as the `capacity_reservation_id` Terraform variable default value is set to `""`.
+
If we were to deploy a workload that requires a GPU and matches the `gpu-inf` NodePool, a spot or on-demand instance would be provisioned instead.
+
In the above EC2NodeClass, the `al2023@latest` AMI alias resolves to the EKS-optimized Amazon Linux 2023 AMI. When Karpenter launches a GPU instance type, it automatically selects the `AL2023_x86_64_NVIDIA` accelerated variant, which includes the NVIDIA driver pre-installed.
+
SOCI is pre-installed on the EKS-optimized AL2023 AMI (> v20250821), so enabling it only requires flipping the `FastImagePull` feature gate via nodeadm NodeConfig in `userData`. No binary downloads or systemd units required. This enables SOCI snapshotter parallel pull and unpack mode, which downloads and unpacks image layers concurrently. This matches what Auto Mode does on G, P, and Trn instances. The `containerd.config` block tunes the SOCI snapshotter for ECR-hosted images:
+
* **`max_concurrent_downloads_per_image: 20`** allows up to 20 layer downloads in parallel per image. Default is 3 on Bottlerocket and 20 on AL2023. Recommended value for ECR.
* **`concurrent_download_chunk_size: "16mb"`** splits each layer into 16 MB chunks downloaded in parallel via HTTP range requests. Recommended for registries that support range GETs (ECR does).
* **`max_concurrent_unpacks_per_image: 12`** unpacks up to 12 layers at once. Default is 1 on Bottlerocket and 12 on AL2023.
* **`discard_unpacked_layers: true`** deletes compressed layer blobs after unpacking to save disk space.
+
**A note on storage for SOCI**
+
SOCI writes image layer blobs to disk while pulling, so the speed of the underlying disk directly affects pull time.
+
GPU instance families (G, P, Trn) come with a local NVMe instance store disks attached to the host. These are significantly faster than EBS and are included in the instance price. `instanceStorePolicy: RAID0` tells Karpenter to assemble all available NVMe disks into a RAID-0 array and relocate `/var/lib/containerd`, `/var/lib/kubelet`, and `/var/log/pods` onto it. This moves the containerd image cache off of the root EBS volume and onto the local NVMe, which is where the SOCI parallel mode speedup actually comes from on these families.
+
For instance types without a local NVMe (most M, C, and R families), `instanceStorePolicy: RAID0` has no effect. In that case SOCI writes to the root EBS volume, which defaults to `20 GiB` gp3 at `3000` IOPS and `125 MiB/s` throughput. That default is sufficient for normal workloads, but becomes the bottleneck when pulling a 10 GiB ML image. If you plan to run SOCI on non-NVMe instances, bump the root volume via `blockDeviceMappings` at the top level of the EC2NodeClass `.spec` (same level as `instanceStorePolicy` and `userData`):
+
[source,yaml]
----
spec:
  # ... other fields ...
  blockDeviceMappings:
    - deviceName: /dev/xvda
      ebs:
        volumeSize: 100Gi
        volumeType: gp3
        throughput: 1000
        iops: 16000
----
+
For more SOCI tuning options (concurrent downloads per image, chunk size, and so on), see the https://github.com/aws-samples/karpenter-blueprints/tree/main/blueprints/soci-snapshotter[Karpenter SOCI blueprints].

+
We now need to create an ODCR and inject it into the corresponding EC2NodeClass and NodeClass to be able to consume it.

## Set up monitoring

Kubernetes users often use Prometheus for metrics collection, but managing long-term metrics storage, high availability, and aggregation across multiple clusters adds operational complexity. In this guide we use Amazon Managed Prometheus (AMP) to handle metrics storage so that metrics persist even when GPU nodes are interrupted or scaled down. AMP also makes it easy to aggregate metrics from multiple clusters in a single query endpoint. We will use the https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack[kube-prometheus-stack] Helm chart to scrape metrics from the cluster and remote-write them to AMP.

For visualization, Amazon Managed Grafana (AMG) is available but requires Active Directory integration for authentication, which is beyond the scope of this guide. Instead, we will use the self-managed Grafana that includes the kube-prometheus-stack Helm chart.
